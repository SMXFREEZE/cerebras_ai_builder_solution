Hi, this is AssetOps, my Cerebras AI Builder Challenge submission.

The product is a scanner-first asset control tower for manufacturing teams. The core problem is drift: operations knows state and custody, facilities knows rack position, and finance knows capitalization status. If one physical scan only updates one system, the manager inherits a diff instead of an answer.

I built the experience around two users. First, a technician at the dock late at night, wearing gloves, with a scanner in one hand and hardware in the other. Second, a manager before standup, with about a minute to understand what needs action.

On the technician side there are four workflows: receive, store, deploy, and transfer. The keyboard scanner path is first class because handheld scanners act like keyboards. The scan input autofocuses, refocuses if the page loses focus, and the camera path sits beside it as a fallback for phones. Store, deploy, and transfer are intentionally two step flows: scan the asset, preview the current record, then scan the destination or receiving badge. That preview is there to catch wrong tag mistakes before a write happens.

Here is a confusing receive. The asset tag already exists, but with a different serial. The screen shows both serials so the technician can compare the physical label to the system record. This is more useful than a generic failure message.

Deploy is where the three-system part matters. If the rack location is missing the RU, the workflow blocks before any downstream writeback runs. When the deploy is complete, the server route writes operations, facilities, and finance. The browser never receives the API token.

The piece of microcopy I would walk through is the deploy success copy: Facilities rack assignment written. Finance capitalization written. I chose those words because they name the side effects that actually happened. It does not just say success. In a future version, if one side effect failed, that missing line would be meaningful.

Transfer is a two-sided custody handoff. The logged-in user is the from side automatically. The receiving badge is explicit, and the asset stays in service.

For managers, I did not start with a big generic table. The manager page opens with a standup brief, action counts, filters, and then the asset table. The asset detail page treats the event log as the forensic source of truth, newest first.

The reconciliation report is server side. It joins operations, facilities, and finance, then translates differences into manager language: Fix today, Needs a human, Probably fine, and Clean. The goal is not to dump raw diffs. The goal is to tell a Monday morning asset manager what to do next.

One call I nearly made the other way was skipping the asset preview between scan step one and step two. That would have been simpler: scan an asset, scan a shelf or badge, and let the API validate. I kept the preview because the extra GET request is cheap, but sending a person back to the wrong rack is expensive. The preview is the cheapest moment to catch a bad scan.

I also chose not to build offline mode, RMA screens, full auth, and bulk import. Those would add surface area without improving the core challenge. For this prototype, I wanted the hot path, the audit trail, and the reconciliation logic to feel reliable.

The README documents the tradeoffs, the pushback on the brief, the writeback rules, what was intentionally not built, and the validation evidence. The app includes scannable Code 128 barcodes for the review cases, so the workflow can be tested with real scanner input.

That is AssetOps: one scan, three systems, and a manager view that turns drift into action.
