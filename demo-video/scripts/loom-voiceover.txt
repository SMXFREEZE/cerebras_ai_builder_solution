This is AssetOps, a scanner-first asset tracking system for Cerebras manufacturing. This walkthrough is generated from the live app with Playwright after a reset, so the scans, errors, writebacks, filters, and audit pages are all being exercised, not mocked in the video.

The product starts with the problem: operations, facilities, and finance each hold a partial truth. The app is built so a technician can scan quickly, while a manager can see which differences actually need action.

On the technician console there are four required flows: receive, store, deploy, and transfer. Each card says which downstream systems it writes, because the safest scan is the one that changes only the records it is supposed to change.

Receive starts at the dock. The serial, model, class, and receiving location are visible before the tag scan. The scan field is focused for USB or Bluetooth scanners, and the camera button is available for a phone. Here I scan a fresh tag and the app confirms the receipt. I scan the same tag again with the same serial to show idempotency. Then I change the serial and scan the tag again. The error shows expected serial and scanned serial, which is the recovery path a tired technician needs.

Store is a two-step flow. First the asset tag is scanned, then the app previews the current asset before asking for the shelf. One call I nearly made the other way was removing this preview and sending both scans straight to the API. I kept it because one extra read is cheap, but walking back to the wrong rack is expensive.

Deploy is stricter because it creates downstream side effects. I first scan a rack without an RU. The app blocks it locally and says the rack unit is missing. Nothing has been written yet. Then I scan the complete rack. This is the important success copy: Facilities rack assignment written. Finance capitalization written. I chose those words because they name the actual systems that changed. Generic success would hide the riskiest part of the workflow.

Transfer is custody only. The from user is the logged-in technician, so the receiving badge is the only explicit badge scan. The app rejects transferring to yourself, then accepts a real receiving badge. The state stays in service; only the custodian changes.

I also show the store-from-in-service case because it is easy to miss. When an in-service asset is stored back on a shelf, the app writes the operations state and clears the facilities rack assignment. Finance is not touched.

Now the manager view. This is designed for the 8:55 AM standup. It starts with the first exception, counts of critical, review, and clean assets, and then the searchable asset table. I filter to the asset we just scanned and open the detail page. The detail page shows current placement, procurement context, and the event log, so the manager can audit receive, store, deploy, transfer, and de-rack behavior.

The reconciliation page joins operations, facilities, and finance server-side so the browser never receives the API token. It does not just diff rows. It ranks differences as fix today, needs a human, probably fine, or clean, then gives each row a recommendation.

Finally, the barcode sheet is the reviewer kit. It includes fresh demo tags, seeded in-service and stored assets, drifted assets, disposed assets, a ghost finance-only tag, locations, a complete deploy rack, an incomplete rack, and user badges. That lets someone test the happy path and the failure cases with a real scanner.

What I built is not every possible enterprise feature. I intentionally left out auth, offline mode, RMA screens, bulk import, and hardware pairing. The prototype focuses on the hot path, scoped writebacks, evidence, and reconciliation judgment.
